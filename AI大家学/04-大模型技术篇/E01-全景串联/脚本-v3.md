## 【第一块：LLM — 大语言模型】（~2min）

LLM，全称 Large Language Model，大语言模型。

你现在用的 DeepSeek、Qwen、Kimi、GPT，底层全是用的Transformer这个基础架构。它的核心能力说出来其实挺朴素的——**给一段文字，预测下一个最可能出现的词**。

就这么简单？对，就这么简单。但这个"简单"的事情做到极致之后，涌现出来的能力是惊人的。

举个具体例子。我给你一句话：

> "今天天气真好，我们去公园___"

你会填什么？"散步"、"玩"、"跑步"——都有可能。LLM 做的事情和你一样，只不过它不是在脑子里猜，而是通过一个复杂的数学函数，基于训练时看过的几千亿字的文本，算出每个候选词的概率。

但这个"算概率"的过程，不是简单的"这个词在前面出现过几次"这种统计。它靠的核心机制叫 **Attention（注意力）**。

什么意思呢？再看一个例子：

> "小明在**北京**参加了一场关于___的学术研讨会。"

要填这个空，模型不能只看"关于"后面的内容，它需要同时关注到"北京"和"学术研讨会"这两个关键信息，把它们综合起来判断。这个"同时看到并关联远距离信息"的能力，就是 Attention。

（画面提示：展示一个简化的 Attention 连线图，"北京"和"学术研讨会"两个词用亮色线连到空格处）

所以你可以把 LLM 理解成：**一个通过 Attention 机制来理解上下文关系，然后预测下一个词的概率机器。**

那问题来了——这个东西原理又不新，Transformer 论文 2017 年就发了，为什么到 2022 年底 ChatGPT 才突然爆火？

这不是一个技术突破的故事，是**五个因素叠加**的结果：

**1. 自回归语言模型（Autoregressive LM）**：就是刚才说的"预测下一个词"。它不是从头生成一整段话，而是一个词一个词地往外蹦，每一步都基于前面所有已生成的内容。这就像你写作文——你写下一句的时候，脑子里想的是前面写了什么。这个机制简单但强大，当模型足够大的时候，"预测下一个词"这件事本身就逼着它去理解语法、逻辑、甚至推理。

**2. 海量无监督预训练**：GPT-3.5 训练时"吃"了大概 4500 亿个 Token 的文本——维基百科、网页、论坛、书籍……什么都有。没人给它标注"这句话是什么意思"，它就是纯粹地做一件事：看前文，猜后文。但你猜几千亿字的"猜词游戏"打下来，它学到的远不止语法——它隐式地学到了事实、常识、甚至一些推理模式。

**3. 大量代码训练**：这是个常被忽略的关键因素。GPT 的训练数据里有大量代码（GitHub 上的开源项目等）。代码有什么特别的？代码是**高度结构化、有严格逻辑**的文本。模型在学"预测下一行代码"的过程中，隐式地学会了逻辑推理、条件分支、变量追踪这些能力。这也是为什么大模型写代码的能力往往超出你的预期——代码训练本质上是在给模型做"逻辑训练"。

**4. 有监督指令微调（SFT）**：预训练出来的模型其实很"野"——你问它"北京在哪"，它可能不是回答你，而是续写"北京在哪？让我们来看看百度百科……"。因为它学的就是"续写"，不是"回答问题"。SFT 这一步就是拿一批高质量的"问题→标准回答"数据，让模型学会"哦，用户问我的时候，我应该回答，而不是续写"。这一步之后，模型才从"文本续写器"变成了"对话助手"。

**5. RLHF（基于人类反馈的强化学习）**：SFT 之后模型能回答了，但回答质量参差不齐。RLHF 就是让人类标注员给多个回答打分——哪个更好、哪个更安全、哪个更有帮助——然后训练一个"奖励模型"来模拟人类的偏好，再用强化学习让大模型朝着"人类觉得好的回答"去优化。这就是为什么 ChatGPT 的回答感觉特别"像人"、特别"懂事"——它是被人类偏好调教过的。

（画面提示：五步堆叠图，从底层"自回归架构"往上依次叠加"预训练→代码训练→SFT→RLHF"，每层标注一句话说明）

所以 GPT-3.5 的爆火不是因为发明了某个新算法，而是这五层东西叠在一起，产生了质变。每一层解决一个不同的问题：架构让它**能学**，预训练让它**学得广**，代码训练让它**学得深**，SFT 让它**会对话**，RLHF 让它**说得好**。

### 补充：MoE 和多模态——2025-2026 的两大进化方向

到这里我们讲的都是"一个模型从头到尾处理所有事情"。但 2025 年之后，大模型架构出现了两个重要的变化：

**MoE（Mixture of Experts，混合专家）**：想象一个公司有 100 个专家，但每个项目只需要请 3 个来开会。MoE 就是这个思路——模型内部有很多组"专家"子网络（比如 256 组），但每次处理一个 Token 时只激活其中几组。这样模型总参数量可以做得很大（知识储备多），但每次推理的计算量却不大（只请相关专家）。DeepSeek-V4 就用了这个架构——总参数 1.6 万亿，但每次推理只激活约 49B 参数，上下文窗口达到了 100 万 Token。这也是为什么 DeepSeek 又快又便宜的一个重要原因。

**多模态（Multimodal）**：最早的 LLM 只能处理文字。但现在主流模型——GPT-4o、Qwen-VL、Claude——都能同时"看"图片、"听"语音、甚至"理解"视频。它们的做法是在 LLM 前面加一个"翻译层"，把图片、语音等非文本信息转换成 LLM 能理解的 Token 序列。所以本质上还是"预测下一个 Token"，只不过 Token 的来源从纯文字扩展到了多种模态。

（画面提示：MoE 示意图——一个大圆里有很多小圆（专家），其中几个亮起；多模态示意图——图片/语音/视频三条线汇入一个"翻译层"，再进入 LLM）

好，理解了 LLM 是什么以及它怎么来的之后，接下来我们看一个更底层的东西——模型是怎么"读"你的文字的。

## 【第二块：Token — 模型的最小阅读单位】（~1.5min）

LLM 是"预测下一个词"的机器。但这里有个问题——**模型不认识"字"，也不认识"词"，它认识的是 Token。**

Token 是什么？简单说就是模型把文本切成的碎片。

看个真实的例子。我用 Qwen 的 Tokenizer 跑了一句话：

> "我喜欢吃苹果"

你猜切成几个 Token？不是 5 个字，也不是 1 个词。它被切成了：

```
我 | 喜 | 欢 | 吃 | 苹 | 果
6 个 Token
```

但英文不一样：

> "unbelievable" → `un` + `believ` + `able` = 3 个 Token

为什么？因为 Token 的切分规则来自一个叫 **BPE（字节对编码）** 的算法。它的核心思想就一句话：**从训练语料里统计出哪些字符组合出现最频繁，把它们合并成一个 Token。**

我用 Hugging Face 教程里的经典例子给你演示完整过程。假设训练语料里有这些词：`"low"` 出现了 5 次，`"lower"` 出现了 2 次，`"lowest"` 出现了 1 次。

**第一步：拆成最小单位。** 每个字符都是一个独立符号，词尾加一个特殊标记 `_`（用来区分独立的 "low" 和 "lower" 里的 "low"）：

```
low    → l o w _      （×5）
lower  → l o w e r _  （×2）
lowest → l o w e s t _（×1）
```

**第二步：统计所有相邻字符对的出现频率。** 这一步是关键——不是随便合并，而是**数出来**谁最常见：

| 字符对 | 出现次数 |
|--------|---------|
| (l, o) | 5+2+1 = **8** ← 最高 |
| (o, w) | 5+2+1 = 8 |
| (w, _) | 5 |
| (w, e) | 2+1 = 3 |
| (e, r) | 2+1 = 3 |

**第三步：合并频率最高的那对。** `(l, o)` 出现 8 次，合并成 `lo`，加入词表：

```
low    → lo w _      （×5）
lower  → lo w e r _  （×2）
lowest → lo w e s t _（×1）
```

**第四步：重新统计，继续合并。** 现在 `(lo, w)` 出现 8 次，最高，合并成 `low`：

```
low    → low _       （×5）
lower  → low e r _   （×2）
lowest → low e s t _ （×1）
```

然后是 `(low, _)` 出现 5 次 → 合并成 `low_`。再然后是 `(e, r)` 出现 3 次 → 合并成 `er`……如此反复，直到达到预设的词表大小（比如 5 万个 Token）。

（画面提示：BPE 合并过程动效——字符逐步合并，频率数字用亮色标注，每步合并时数字高亮闪烁）

最终你会得到一个**有序的合并规则列表**——按频率从高到低排列。这个列表就是 Tokenizer 的核心。之后遇到任何新文本，就按这个顺序去"套"——能合并的就合并，合并不了的就保持拆开。

这就是 BPE 的精妙之处：高频词（如 "the"、"is"）会被合并成一个 Token，罕见词会被拆成子词（subword）片段。比如 `"unbelievable"` 可能被切成 `un` + `believ` + `able` 三个子词——模型虽然没见过这个词，但它认识 "un"（否定前缀）、"believ"（相信）、"able"（能够），可以通过子词组合**猜出**大致含义。

这也解释了为什么不同模型的切分结果不一样——每个模型的训练语料不同，统计出来的合并顺序就不同，最终的词表也就不一样。

**不同模型的 Tokenizer 也不一样。** 同样是"我喜欢吃苹果"这句话：

| 模型 | Tokenizer | Token 数 | 切分方式 |
|------|-----------|---------|---------|
| Qwen | qwen-tokenizer | 6 | 我\|喜\|欢\|吃\|苹\|果 |
| GPT-4 | tiktoken | 5 | 我\|喜欢\|吃\|苹果 |
| Claude | claude-tokenizer | 6 | 我\|喜\|欢\|吃\|苹\|果 |

为什么不一样？因为每个模型的训练数据不同，BPE 统计出来的高频组合也不同，最终生成的词表（vocabulary）就不一样。GPT 的词表里有"喜欢"这个合并项，Qwen 的没有，就这么简单。

**Token 还直接决定了你的使用成本。** 所有大模型 API 都是按 Token 计费的。举个例子，假设你调用 GPT-4o：

- 输入价格：$2.5 / 百万 Token
- 输出价格：$10 / 百万 Token

你问了一句中文问题（50 Token），模型回了一段中文回答（500 Token），这一次调用的成本就是：

```
输入：50 × $2.5/1M = $0.000125
输出：500 × $10/1M = $0.005
合计：约 $0.005（≈ 0.036 元人民币）
```

看起来不多对吧？但如果你是做一个面向用户的产品，每天 10 万次调用，一个月就是 1000 多美元。**同样的内容，中文消耗的 Token 数通常比英文多 1.5 到 2 倍**，这也是为什么有些 API 中文调用比英文贵。

另外，Tokenizer 还会生成一些你看不到的**特殊 Token**，比如：
- `<bos>`（Beginning of Sequence）：标记一段文本的开头
- `<eos>`（End of Sequence）：标记文本结束，模型看到这个就知道该停下来了
- `<pad>`（Padding）：补齐用的，让不同长度的输入对齐

这些特殊 Token 不承载语义，但它们对模型的运行机制至关重要——比如模型生成回答时，就是不断预测下一个 Token，直到预测出 `<eos>` 才停止。

好，现在我们知道模型通过 Token 来"读"文字了。那下一个问题就是——模型一次能"读"多少 Token？

## 【第三块：Context & Context Window — 大模型没有"记忆"】（~1.5min）

这是很多人没意识到的一个关键点：**大模型每次对话，都是"失忆"的。**

什么意思？你看下面这个场景：

你在 Kimi 里问了一个问题："帮我写一个 Python 的快速排序"。它给你写好了。然后你接着问："把它改成降序排列"。它也能改。

看起来它"记住"了上一轮对话对吧？其实没有。

**真相是：你的客户端（比如 Kimi 的 App）在每一轮对话时，都把前面所有的聊天记录重新发给了模型。** 模型每次收到的都是完整的对话历史，然后只生成最新一轮的回答。

来看实际的 API 请求长什么样：

**第一轮请求：**
```json
{
  "messages": [
    {"role": "user", "content": "帮我写一个Python的快速排序"}
  ]
}
```
模型返回了一大段排序代码。

**第二轮请求（你说"改成降序"时）：**
```json
{
  "messages": [
    {"role": "user", "content": "帮我写一个Python的快速排序"},
    {"role": "assistant", "content": "def quick_sort(arr): ...（第一轮的完整回答）"},
    {"role": "user", "content": "把它改成降序排列"}
  ]
}
```

看到了吗？第二轮请求里，**第一轮的问题和回答全都在**，一起重新发给模型。模型并不是"回忆"起了上一轮——它是重新"读"了一遍全部对话，然后回答最新的问题。

这就引出了两个概念：
- **Context（上下文）**：你发给模型的这整段内容，就叫上下文
- **Context Window（上下文窗口）**：模型一次能"读"的最大 Token 数量

现在主流模型的窗口大小：GPT-5 是 400K Token，Claude 和 Kimi K3 都达到了 100 万，DeepSeek-V4 也是 100 万。100 万 Token 大概是 80 万汉字左右，听起来很多对吧？

但有个坑。有研究团队做了一个实验：把关键信息放在一段长文本的不同位置，然后问模型。结果发现——**放在开头和结尾的信息模型能很好地回答，放在中间的信息经常被忽略。** 这个现象有个专门的名字叫 **"Lost in the Middle"**。

（画面提示：一个长条形，两端绿色中间红色，标注"注意力衰减"）

所以再大的窗口也不等于所有信息都能被完美处理。这也是为什么在实际应用中，怎么管理 Context 成了一门学问。

### 补充：KV Cache — 为什么多轮对话越来越慢？

你可能还注意到一个现象：跟 AI 聊天的时候，前几轮回复很快，聊久了越来越慢。这不是你的错觉。

原因是这样的。模型在处理每一轮 Context 时，会为每个 Token 计算一对 Key-Value（你可以理解成一种"中间计算结果"）。这些中间结果会被缓存起来，叫做 **KV Cache**。

第一轮对话只需要算 100 个 Token 的 KV Cache。第二轮要算 300 个（包含了第一轮的内容）。到了第十轮可能要算 5000 个。虽然前面轮次的 KV Cache 可以复用不用重算，但**新增的 Token 仍然需要计算，而且整体管理的开销也在增长**。

更重要的是，KV Cache 要占显存。一个大参数模型处理超长 Context，光 KV Cache 就要占几十 GB 的显存。这也是为什么超长上下文的推理成本非常高——不是模型变笨了，是"记忆"的物理代价在增长。

理解了模型每次都在重新"读"你的全部对话之后，一个很自然的问题就是——你往这个 Context 里放什么内容，直接决定了模型回答的质量。

## 【第四块：Prompt & System Prompt — 你怎么问，决定它怎么答】（~1.5min）

你发给模型的这整段输入文字，就叫 **Prompt**。

但同样的模型，不同的问法，效果差距巨大。看个对比：

**Prompt 1：**
> "帮我写个排序算法"

模型可能给你冒泡排序、给你插入排序、给你解释什么是排序……不确定，看它心情。

**Prompt 2：**
> "用 Python 实现快速排序，输入是整数列表，要求原地排序，返回升序结果，时间复杂度 O(n log n)"

这个结果就很确定了。为什么？因为你在 Prompt 里放了更多的**约束条件**，相当于缩小了模型"预测下一个词"时的搜索空间。

所谓 Prompt Engineering（提示词工程），说白了就是研究怎么把你的需求说得更精确、更结构化，让模型更容易给出你想要的答案。

这里面有两个非常实用的技巧值得了解：

**Few-shot（少样本学习）**：在 Prompt 里给模型几个"示范"，它就能照着来。比如：

```
把以下中文翻译成英文：
中文：你好 → 英文：Hello
中文：谢谢 → 英文：Thank you
中文：再见 → 英文：
```

模型看到前两个例子的模式，就知道你要做什么，直接输出 "Goodbye"。不需要任何训练，只需要在 Prompt 里给几个例子就行。给 0 个例子叫 Zero-shot，给几个就叫 Few-shot。

**CoT（Chain of Thought，思维链）**：让模型"一步步想"，而不是直接给答案。比如：

```
普通问法：一个班有 30 人，男生比女生多 6 人，男生几人？
→ 模型可能直接猜一个数

CoT 问法：请一步一步思考。一个班有 30 人，男生比女生多 6 人，男生几人？
→ 模型会写出：设女生 x 人，男生 x+6 人，x + x+6 = 30，2x = 24，x = 12，男生 = 18
```

就是在问题前面加一句"请一步一步思考"，准确率就能从 17.7% 飙升到 78.7%（这是原始论文在 GSM8K 数学推理数据集上的实验结果）。为什么？因为直接回答时模型在"猜最终答案"，而 CoT 让模型在"推理每一步"——推理比猜测容易得多。

### System Prompt — 给模型设"人设"和"规矩"

但你有没有发现一个问题——**每次对话你都得重新说一遍"我要 Python"、"我要简洁的代码"？** 能不能一次性设好？

能。在 API 调用里，消息有个字段叫 `role`，它可以是三种值：`user`（用户说的）、`assistant`（模型回复的）、还有一种叫 `system`。

System 消息放在 messages 数组的最前面，它就是你给模型设的"人设"和"规矩"，用户看不到，但模型每次回答都会遵守。

看个真实的例子。比如你在做一个客服机器人：

```json
{
  "messages": [
    {
      "role": "system",
      "content": "你是XX公司的智能客服。你的职责是帮助用户解决订单相关问题。规则：1. 语气友好专业 2. 不讨论竞品 3. 不确定的问题转人工 4. 回答控制在100字以内"
    },
    {"role": "user", "content": "我的订单怎么还没发货？"}
  ]
}
```

这个 System Prompt 就相当于给新员工发的内部手册——你是谁、你的边界在哪里、你不能做什么。

这里我要说一个很多开发者都不知道的事情：**从技术实现上看，System Prompt 和 User Prompt 没有任何本质区别。** 它们都是 Token，都会被模型读到，都进入同一个 Context Window。`role: "system"` 只是 API 层面的一个标记，告诉模型"这段话的优先级更高"，但模型内部并不会对它们做不同的处理。

所以你可以这样理解：**System Prompt 就是一个被放在最前面的、优先级更高的 Prompt。**

好了，从 Prompt 到 System Prompt，你大概已经发现我们一直在做同一件事——**想办法往 Context Window 里塞更好的信息**。但不管你怎么塞，再大的窗口终究有限。你公司有几千份内部文档、几万个客户工单、几十 TB 的行业报告——不可能全部塞进去。那怎么办？

要回答这个问题，我们先学一个关键的基础技术——Embedding。

---

## 【第五块：Embedding — 让文字变成"坐标"】（~1min）

还记得第二块讲的 Token 吗？Token 只是一串数字编号（比如"苹果"在某个 Tokenizer 里可能是编号 34521），这个编号本身不包含任何语义信息——编号 34521 和编号 34522 在模型看来，跟编号 1 和编号 10000 的距离是一样的。

那模型怎么知道"苹果"和"水果"很接近，而和"汽车"差很远？

答案是 **Embedding（向量嵌入）**。

Embedding 做的事情是：**把每个 Token（或一段文本）映射成一个高维空间里的"坐标点"。** 语义越接近的词，在空间里的距离越近。

举个直观的例子。假设我们把词映射到一个二维平面上（实际是高维的，比如 1536 维，但二维好理解）：

```
        水果
       /    \
    苹果    香蕉
                \
                橙子

    汽车 —— 卡车 —— 公交
```

"苹果"和"水果"很近，"苹果"和"汽车"很远。模型就是通过这种空间距离来"理解"语义关系的。

（画面提示：二维词向量可视化动效——词语在平面上以点呈现，相近的词聚成簇）

顺便说一句，这些 Embedding 是怎么训练出来的？核心方法叫**对比学习（Contrastive Learning）**。思路非常直觉：把语义相似的文本对（比如同一个问题的两种不同表述）在向量空间里**拉近**，把语义不相似的文本对**推远**。训练几千轮之后，模型就学会了"语义相近 = 向量接近"这件事。OpenAI 的 text-embedding 模型、Sentence-BERT 这些主流 Embedding 模型，背后都是这套方法。

但 Embedding 不只是用在模型内部。它还是一个极其重要的**外部工具**。

具体来说，你可以把一整段文本（比如一篇文档、一条客户反馈）通过一个 Embedding 模型变成一个向量（一串数字），然后存进数据库。之后用户提问时，也把问题变成向量，通过计算向量之间的距离来找到语义最相关的文档。这就是所谓的**语义搜索**——不是靠关键词匹配，而是靠"意思接近"。

记住这个概念，因为接下来要讲的 RAG 就是直接建立在 Embedding 之上的。

**一句话总结：Token 是模型识别文字的"编号"，Embedding 是给这些编号赋予"语义坐标"的过程。**

---

## 【第六块：RAG + 向量数据库 — 让 AI 查资料再回答】（~1.5min）

刚才讲了 Embedding 可以把文本变成向量、实现语义搜索。现在把这个能力用起来，解决一个很现实的问题——**怎么让 AI 访问它训练时没见过的知识？**

答案就是 **RAG（Retrieval-Augmented Generation，检索增强生成）**。

思路非常直白：**让 AI 先查资料，再回答。**

具体分三步走：

**第一步：建库。** 把所有文档切成小段（比如每段 500 字），然后通过 Embedding 模型把每段变成一个向量，存进**向量数据库**。

这里插一句什么是向量数据库。普通数据库存的是文字、数字，靠关键词匹配来搜索。向量数据库存的是"向量"（一串数字），靠**向量距离**来搜索——距离越近，语义越相关。主流的向量数据库有 Pinecone、Milvus、Weaviate、Chroma 等。

**第二步：检索。** 用户提了一个问题，比如"我们公司 2025 年 Q3 的退货率是多少"。先把这个问题也通过 Embedding 模型变成向量，然后去向量数据库里找**语义最接近**的几段文档。

**第三步：生成。** 把检索到的几段文档塞进 Context Window，连同用户的问题一起发给 LLM。LLM 基于这些"参考资料"来回答，而不是凭空编造。

（画面提示：RAG 三步流程图——建库（文档→切片→向量→数据库）→ 检索（问题→向量→搜索）→ 生成（文档+问题→LLM→回答））

整个流程可以用一句话总结：**RAG = 搜索引擎 + 大模型。** 搜索引擎负责找到相关资料，大模型负责把资料"翻译"成人话回答你。

**RAG 解决了 LLM 的三个硬伤：**
1. **知识截止**：模型训练数据有截止日期，RAG 可以实时检索最新信息
2. **幻觉问题**：模型可能编造不存在的信息，RAG 让它基于真实文档回答，减少胡说八道
3. **私有知识**：模型不知道你们公司的内部信息，RAG 可以把企业文档变成 AI 的知识库

这也是为什么 2025-2026 年企业 AI 落地最多的场景就是 RAG——客服机器人、内部知识问答、智能文档助手，背后几乎全是这套方案。

**那 RAG 和 Fine-tuning（微调）有什么区别？** 这是一个经常被问到的问题。简单说：
- **RAG** 像开卷考试——给你参考资料，你照着回答。优点是成本低、可以随时更新资料、有引用来源。
- **Fine-tuning** 像上课学习——用你的数据继续训练模型，把知识"烧进"模型权重里。优点是回答更快更自然，缺点是成本高（需要 GPU 训练）、更新知识得重新训练。

实际项目中，两者经常结合使用：用 Fine-tuning 让模型学会你的行业术语和表达风格，用 RAG 提供具体的事实信息。

---

## 【第七块：Tool / Function Calling — 从"会说"到"能做"】（~2min）

好，到这儿我们讲的全都是"模型怎么说"。但现实场景里，我们经常需要模型**去做事**——查天气、读数据库、发请求。

LLM 天生是不会做这些事情的。它就是个文本预测机器，你让它查天气，它只能"编"一个温度出来。

那怎么办？答案是 **Function Calling（函数调用）**——给模型描述它有哪些"工具"可以用，让它在需要的时候输出一个结构化的调用指令，由你的程序去真正执行，然后把结果喂回给模型。

看个实际的请求：

```json
// 第一步：你告诉模型"你有这些工具可以用"
{
  "messages": [
    {"role": "user", "content": "北京今天多少度？"}
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "查询城市天气",
        "parameters": {
          "type": "object",
          "properties": {
            "city": {"type": "string", "description": "城市名"}
          }
        }
      }
    }
  ]
}
```

```json
// 第二步：模型返回的不是文字，而是一个结构化的工具调用指令
{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [{
        "function": {
          "name": "get_weather",
          "arguments": "{\"city\": \"北京\"}"
        }
      }]
    }
  }]
}
```

```json
// 第三步：你的程序执行真正的天气查询，把结果喂回去
{"role": "tool", "content": "{\"temp\": 28, \"condition\": \"晴\", \"humidity\": 45}"}
```

```json
// 第四步：模型根据真实数据生成最终回答
{"role": "assistant", "content": "北京今天 28°C，天气晴朗，湿度 45%。"}
```

**整个流程就是：用户提问 → 模型判断要调工具 → 输出调用指令 → 程序执行 → 结果回传 → 模型生成最终回答。**

这里有一个关键的问题——**模型怎么知道什么时候该调工具、调哪个、参数填什么？**

这不是天生的。**是训出来的。**

大模型在预训练之后，还有一个 **指令微调（SFT）** 的阶段。在这个阶段，开发者会构造大量上面那种格式的对话数据——"用户问了一件事 → assistant 不是回复文字而是输出了 tool_calls → tool 返回结果 → assistant 再总结"——然后让模型学习这种模式。

训练数据大概长这样：

```json
{
  "messages": [
    {"role": "system", "content": "你可以使用 get_weather(city) 和 calculate(expr) 两个工具"},
    {"role": "user", "content": "北京和上海的温度差多少？"},
    {"role": "assistant", "content": null,
     "tool_calls": [
       {"function": {"name": "get_weather", "arguments": "{\"city\":\"北京\"}"}},
       {"function": {"name": "get_weather", "arguments": "{\"city\":\"上海\"}"}}
     ]},
    {"role": "tool", "content": "{\"temp\": 28}"},
    {"role": "tool", "content": "{\"temp\": 32}"},
    {"role": "assistant", "content": "上海比北京高 4 度，上海 32°C，北京 28°C。"}
  ]
}
```

模型在训练时看了成千上万条这样的数据对，通过 SFT 学会了三件事：**什么时候该调工具**（而不是自己瞎编）、**该调哪个工具**（从候选列表里选）、**参数怎么填**（从用户的话里抽取关键信息）。

所以 **Tool 能力的本质是：用结构化的对话数据，通过指令微调教会模型在合适的时机输出特定格式的调用指令。**

---

## 【第八块：MCP — AI 世界的 USB-C】（~1min）

Function Calling 解决了"模型能调工具"的问题。但新的问题来了。

想象一下：你有 10 个 AI 应用（ChatGPT、Claude、Kimi、Qwen……），你有 20 个工具（天气、日历、数据库、邮件……）。每个 AI 应用都要对接每个工具，这就是 10 × 20 = 200 次适配开发。每家的 Function Calling 格式还不完全一样——有的用 `function`，有的用 `tool`，有的参数格式不同。

这就像 USB 接口混乱的年代——每个手机一个充电口，出门得带一堆线。

**MCP（Model Context Protocol，模型上下文协议）就是来统一这个标准的。** 它是 Anthropic 在 2024 年底提出的一个开放协议，定义了 AI 应用连接外部工具的统一方式。

（画面提示：左边画一堆杂乱的连线——N×M 适配地狱；右边画一个中心 Hub，AI 应用和工具各连到 Hub——N+M 星型拓扑）

MCP 的架构分三层：
- **Host**：AI 应用（比如你的聊天 App）
- **Client**：连接管理器，一个 Host 可以有多个 Client
- **Server**：工具提供方（天气服务、数据库等，每个 Server 暴露自己的能力）

协议底层基于 JSON-RPC 2.0。Server 可以暴露三种能力：`tools`（可调用的工具）、`resources`（可读取的数据）、`prompts`（可复用的提示词模板）。

到 2026 年，MCP 已经成为事实标准——超过 600 个客户端、3000 多个服务端，连 OpenAI 的 ChatGPT 也加入了支持。你只需要写一个 MCP Server，所有支持 MCP 的应用都能用。一次开发，处处运行。

---

## 【第九块：Agent — 让 AI 自己决定下一步】（~1min）

好，到现在为止，所有流程都是**你说一句，模型做一步**。它不会自己决定下一步该干什么。

Agent 就是把这最后一步也自动化了。

Agent 的核心是一个循环：

```
观察当前状态 → 思考该做什么 → 执行动作 → 观察结果 → 再思考 → ...
```

这个循环有一个学术名字，叫 **ReAct 模式**（Reasoning + Acting）。

举个具体场景。你对一个 Agent 说："帮我调研一下竞品的定价策略，整理成报告"。

一个普通 LLM 只能给你编一段话。但一个 Agent 会这么做：

1. **Think**：需要搜索竞品官网，我先调用搜索工具
2. **Act**：调用 web_search("竞品A 定价策略")
3. **Observe**：拿到了 5 个搜索结果
4. **Think**：信息不够，我需要打开官网看具体价格
5. **Act**：调用 browser.get("https://competitor.com/pricing")
6. **Observe**：拿到了价格页面内容
7. **Think**：差不多了，但还缺竞品 B 的信息……
8. （循环继续，直到信息充分）
9. **Act**：调用 doc.create() 生成报告

支撑这个循环的有四个关键组件：

| 组件 | 作用 | 类比 |
|------|------|------|
| **Planning** | 把大任务拆成小步骤 | 项目经理做 WBS |
| **Memory** | 短期靠 Context Window，长期靠向量数据库 | 便签 + 笔记本 |
| **Tool Use** | 就是前面讲的 Function Calling | 工具箱 |
| **Reflection** | 检查结果对不对，不对就重来 | 做完之后自查 |

**Agent = LLM + Planning + Memory + Tools + Reflection。** 把前面讲所有概念都串起来了。

---

## 【第十块：Agent Skill — 给 AI 一本"操作手册"】（~50s）

Agent 能自主干活了，但你很快会发现一个问题——**每次遇到类似的任务，它都要从头"想"一遍该怎么做。**

比如你经常让 AI 帮你做代码审查（Code Review）。第一次你得详细描述：先看 PR 描述、再对比改动文件、检查命名规范、看有没有潜在的 bug……每次都这么写太累了。

**Agent Skill（智能体技能）就是把这些"最佳实践"封装成可复用的标准化模块。**

你可以把 Skill 理解成一本**操作手册**——它告诉 Agent：遇到这类任务时，按照什么流程走、需要注意什么、输出什么格式。

具体来说，一个 Skill 通常包含：
- **触发条件**：什么情况下使用这个 Skill（比如用户说"帮我 review 代码"）
- **执行流程**：分哪几步、每步做什么
- **约束规则**：有哪些红线不能碰
- **输出模板**：结果的格式要求

来看个实际的例子。Claude Code 里有一个 Skill 叫 `review`，它的核心内容大概是这样：

```markdown
# Code Review Skill

触发：当用户请求代码审查时
流程：
1. 读取变更的文件列表
2. 对每个文件：检查逻辑错误 → 检查命名规范 → 检查性能问题
3. 对发现的问题进行严重性分级（Critical / Warning / Suggestion）
4. 生成结构化报告

约束：
- 不自动修改代码，只报告问题
- Critical 级别的问题必须标注具体行号
```

有了 Skill，Agent 就不是一个"什么都要从零开始想"的新手了——它变成了一个**有经验的老员工**，遇到熟悉的任务直接翻手册按流程走。

**Skill 和 Prompt 的关系是什么？** Skill 本质上就是一套精心设计的 Prompt 模板 + 工作流程。区别在于 Prompt 是你临时写的，Skill 是预先封装好、反复使用的。如果说 Prompt 是即兴发言，Skill 就是排练过的演讲稿。

（画面提示：比喻图——左边是"即兴发言"（零散 Prompt），右边是"排练过的演讲稿"（结构化 Skill），中间一个箭头标注"封装+复用"）

## 【第十一块：Harness Engineering — 让 Agent 靠谱地工作】（~1min）

Agent 听起来很美好对吧？但实际用起来你会发现一个大问题——**不稳定。**

同一个任务，跑一次成功了，跑一次失败了。有时候它会调用错误的工具，有时候陷入死循环，有时候"幻觉"出一个不存在的函数名。

这不是模型不够聪明的问题——**是你给 Agent 搭的工作环境不够好。**

2026 年 AI 圈最火的新概念就是解决这个问题的，叫 **Harness Engineering（驾驭工程 / 支架工程）**。

Harness 直译是"马具"——你不是要训练一匹更好的马，你是要给马套上缰绳和围栏，让它跑在正确的路上。

具体来说，一个 Harness 包含这些东西：

- **Guardrails（安全围栏）**：比如"Agent 永远不能执行删除操作"、"单次任务预算不能超过 10 元"
- **Feedback Loop（反馈回路）**：Agent 每一步的输出都经过自动验证，不对就拦截
- **Audit Trail（审计日志）**：记录 Agent 每一步的思考和决策过程，出了问题可以回溯
- **Fallback（降级机制）**：Agent 连续失败 3 次，自动转人工

这里有一个认知上的升级。AI 工程经历了关键的范式进化：

| 阶段 | 时间 | 关注点 |
|------|------|--------|
| Prompt Engineering | 2023-2024 | 怎么写好一条指令 |
| **Harness Engineering** | **2025-2026—** | **怎么搭一套系统让 AI 可靠地运行** |

一句话总结：**决定 Agent 上限的，不是模型有多强，而是你给它搭的工作环境有多好。**

## 【第十二块：2026 前沿 — OpenClaw、Hermes、Agentic Coding】（~1min）

最后讲三个 2026 年最新的东西，帮你把视野拉到最前沿。

### OpenClaw（小龙虾）

还记得开场那个"养龙虾"的梗吗？OpenClaw 就是这个龙虾。

它不是一个模型，而是一个**开源的 Agent 运行时**。你自己选模型——Claude、GPT、DeepSeek 都行——然后让 Agent 在你的电脑上执行真实的操作：发消息、管文件、控制应用、接 50 多个聊天平台。

上线第二天就突破 10 万 Stars，三个月超过 Linux 成为 GitHub 历史 Star 数第一，目前超过 40 万 Stars，是开源历史上增长最快的 AI 项目。它证明了一件事：Agent 从实验室 Demo 到日常生产力工具，这条路已经走通了。现在生态已经有 4.4 万多个 ClawHub 技能，从个人玩具走向了企业协作。

### Hermes（Nous Research）

Hermes 有两层含义：一层是 Nous Research 做的开源大模型系列（Hermes 4 家族覆盖 14B 到 405B 多个规格，支持"混合推理"——可以快速回答，也可以切换成深度思考模式）；另一层是 2026 年 2 月发布的 **Hermes Agent 框架**。

Hermes Agent 最大的亮点是**自我学习循环**——它在执行任务的过程中会自动总结经验、生成新的"技能"（还记得刚才讲的 Agent Skill 吗？Hermes 可以自动生成这些 Skill），下次遇到类似问题表现更好。简单说就是：**Agent 不只是执行任务，它还在"成长"。** 2026 年 2 月上线后增长迅猛，目前 GitHub 已超过 22 万 Stars，日活跃用户甚至超过了 OpenClaw。

### Agentic Coding

Karpathy（前 OpenAI / Tesla AI 负责人）在 2026 年提出的概念。他之前提过一个词叫"Vibe Coding"——用嘴说需求让 AI 写代码。后来他自己说 Vibe Coding 只是玩具阶段，真正要做生产级的事，需要的是 **Agentic Coding**——让 AI Agent 自主完成从需求分析、架构设计到编码部署的全流程。现在已经形成四大阵营：CLI Agent（Claude Code、Codex CLI）、AI IDE（Cursor 3.0、Windsurf）、全天候自主 Agent（Devin、Hermes Agent）、开源方案（OpenClaw、Cline）。人的角色从"写代码"变成了"做决策和审核"。

## 【收尾 — 一张图打通全局】（~40s）

好，最后我把今天讲的所有概念用一张图串起来：

（画面提示：从左到右的递进图，每个节点连到下一个，米色系温馨配色）

```
LLM（只会预测下一个词）
 ↓
Token（模型阅读的最小单位）
 ↓
Context Window（每次能"看到"的信息上限）
 ↓
Prompt / System Prompt（你往窗口里放什么信息）
 ↓
Embedding（给Token赋予语义坐标）
 ↓
RAG + 向量数据库（让AI先查资料再回答）
 ↓
Function Calling / Tool（通过SFT训练，让模型能调工具）
 ↓
MCP（统一工具接口的行业标准）
 ↓
Agent（自主决策循环：观察→思考→行动→反思）
 ↓
Agent Skill（封装最佳实践，让Agent有经验可用）
 ↓
Harness Engineering（约束+反馈+审计，让Agent可靠运行）
 ↓
OpenClaw / Hermes / Agentic Coding（2026：Agent走进现实）
```

每一个层级都在解决上一个层级的瓶颈：

LLM 只会猜词，所以需要 Token 来定义"猜"的粒度；Token 本身没有语义，而模型每次能"看到"的信息又有限，所以需要管理好 Context 里的信息质量；你往 Context 里放什么直接决定了回答质量，所以需要掌握 Prompt 的技巧；但不管怎么塞，128K 的窗口终究有限，所以需要 Embedding 把外部知识变成可搜索的向量；有了 Embedding 就能实现 RAG，让 AI 按需检索外部资料；模型只会说话不会做事，所以需要 Function Calling 让它能调工具；工具接口太乱，所以需要 MCP 来统一标准；单轮交互不够，所以需要 Agent 来自主循环；Agent 每次都从零开始太浪费，所以需要 Skill 来封装经验；Agent 不稳定，所以需要 Harness 来约束……

**从"猜下一个字"到"自主完成一个项目"，这不是一堆名词的堆砌，而是每一层都在解决上一层解决不了的问题。**

理解这条链，你以后看任何 AI 新闻都不再是碎片。
